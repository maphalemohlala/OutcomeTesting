## A note on what "verified" means here

Three different kinds of evidence appear below, and they are not equally strong.

- **Repo-verified.** Read from source or from the unpacked solution. Cited with a path and line.
- **DEV-verified.** Read from `Env_AQ_Dev` with a read-only query. True of DEV today; **TEST and PROD are not audited** and data-level configuration does not promote.
- **Cannot verify.** Needs a browser, a signed-in user, or an act (an import, an email send) that has not happened. These are **not** marked as passing, and a manual script for each is in section 4.

One structural caveat runs through everything portal-related: **`powerpages/` is hand-authored source, not a mirror of DEV.** A file here can differ from what the site is actually running. Every portal verdict is therefore a verdict on the intended configuration, and the manual script re-checks the ones that matter.

### Change 5 — Checkers edit assigned cases only · **FAIL**

**Checked:** the portal write path end to end, looking specifically for a way round it. I found one.

The architecture is sound. The portal **cannot write `al_outcomecase` directly** — `powerpages/.../table-permissions/Outcome-Case-All-Read.tablepermission.yml` is `adx_write: false`. Edits travel as a JSON payload PATCHed onto the checker's own contact row, and `CaseHeaderRequestPlugin` does the privileged write. The contact id comes from the platform, never the payload (`CaseHeaderRequestPlugin.cs:132-134` comment).

But the authorization is split, and one half is missing a check:

```
CaseHeaderRequestPlugin.cs:151   EnsureCheckerEditable(fields)        // which fields at all
CaseHeaderRequestPlugin.cs:158   if (editsTaxFields)
CaseHeaderRequestPlugin.cs:160       EnsureTaxReviewerRole(...)       // role
CaseHeaderRequestPlugin.cs:161       EnsureTaxReviewOpen(service, caseId)   // <-- caseId only
CaseHeaderRequestPlugin.cs:165   if (fields.Count > 0)
CaseHeaderRequestPlugin.cs:167       EnsureAssignedToCase(service, contactId, caseId)   // assignment
```

`EnsureAssignedToCase` runs **only when `fields.Count > 0`**. A payload that sets only `TaxCheckRequired` and/or `TaxTeamDisposition` has `fields.Count == 0`, so it never runs.

`EnsureTaxReviewOpen` at `CaseHeaderRequestPlugin.cs:436-455` takes `caseId` and no contact. Its only test is that the Tax review is not already submitted:

```csharp
query.Criteria.AddCondition(ReviewCaseAttr, ConditionOperator.Equal, caseId);
query.Criteria.AddCondition(ReviewStatusAttr, ConditionOperator.Equal, StatusSubmitted);
```

**The hole:** any contact holding `AL Portal - Tax Reviewer` can set `al_taxcheckrequired` and `al_taxteamdisposition` on **any case in the system** whose Tax review is unsubmitted — including cases assigned to a different checker. They need only the case id, and `Outcome Case - read all` is global, so every case id is readable.

This is not cosmetic: those two fields **re-derive the review route** (BR-004 / AD-036). One checker can reroute another checker's case.

**Fields exposed:** `CheckerEditable` at `CaseHeaderRequestPlugin.cs:317-333` correctly excludes `al_casereference`, `al_ioreference`, `al_duedate`, `al_casestatus`, `al_priority` and `ownerid`, pinned by `CaseHeaderRequestPluginTests.cs:104-125`. No identifiers are writable.

### Change 10 — Tax → AQS combined remediation · **FAIL**

**The code implements the opposite rule, and says so.**

`plugins/OutcomeTesting.Plugins/OutcomeRules.cs:241-255`:

```csharp
public static int NextCaseStatusForTax(int answerChoice, bool aqsStillToCome, bool remedialActionFlagged)
{
    // OD-027: a Tax non-pass enters remediation whatever the route (BR-006). Only a
    // passed Tax check hands off to AQS — a case whose Tax check failed must not
    // proceed to an advice quality review with the failure unaddressed...
    if (remedialActionFlagged || TaxResultRequiresRemediation(answerChoice))
    {
        return CaseLifecycle.AwaitingRemediation;
    }
    return aqsStillToCome ? CaseLifecycle.Queued : CaseLifecycle.Closed;
}
```

Requirement: *"a Tax fail no longer sends the case to remediation; the case proceeds to AQS."*
Code: a Tax fail **does** send the case to remediation, and **only** a passing Tax check hands off to AQS.

And remediation is still **per check, not per case**. The action's business key is built from the review's sequence:

- `Remediation.cs:58` — `var code = "REM-" + caseReference + "-" + sequence;`
- `SubmitReviewPlugin.cs:1013-1015` — raised inside each review's own submit.

A Tax submit and an AQS submit therefore produce two different codes and two different rows. There is no combining step anywhere.

**Every edge case in the brief is unimplemented**, because the state machine was never changed. Cases already in Tax remediation at deployment are also unaddressed — the `repointremediation` verb exists but repoints existing actions, it does not merge them.

### Fixes 6 — Due Date 72 hours · **Partial**

**What works:**

- `ImportRules.DueDateFor` (`ImportRules.cs:239-242`) — `uploadedAt.AddHours(72)`, calendar time, taken from the upload moment so all cases in one file share a deadline.
- Stamped only at import (`ImportCasesPlugin.cs:175`); nothing recalculates existing cases.
- The sheet's own `DueDate` is deliberately unmapped (`ImportRules.cs:206-211`) — that column is IO's deadline for the paraplanner, not this system's for the check.
- Editable, gated by a new `case.duedate` capability at Edit, enforced server-side in `UpdateCaseDetailsPlugin` before the record is read.

**Gap 1 — the column is DateOnly, so "72 hours" is not what is stored.** `al_duedate` is `Behavior 2` (DateOnly) in `src/Entities/al_OutcomeCase/Entity.xml`. `DueDateFor` returns a `DateTime` carrying a time of day, and Dataverse discards it. DEV confirms — **every** `al_duedate` value is `T00:00:00`.

So the effective rule is "the date three days later", not "72 hours later". The claim in the commit message and `docs/deployment/2026-09-19-due-date-default-and-manager-edit.md` that the deadline "keeps the time of day" is **wrong once stored**, and a unit test asserts a property of the return value that never reaches the database.

**Gap 2 — a BST off-by-one follows from Gap 1.** `uploadedAt` is UTC. An upload at 23:30 UTC on 17 September is 00:30 **BST on the 18th** to a UK user. `+72h` = 23:30 UTC on the 20th, stored as **20 September**. The user uploaded on the 18th and expects the 21st. The date rules elsewhere are careful about exactly this (`CaseHeaderRules.UkDate`, `ukToday()`); the due-date derivation is not.

**Gap 3 — never exercised.** DEV-verified: the newest import batch is **2026-09-16**, before the rule landed on 2026-09-19. **No case has been imported since.** The default is proven by unit tests only.

**Gap 4 — the permission does not promote.** `al_pagepermission` rows are data. See Finding 4.

## 3. Findings by severity

### CRITICAL — RESOLVED

**Finding 1 — Every signed-in portal user can read every case, every answer and every remediation action.**

> **FIXED `71a3e08` (2026-09-20).** The project owner's direction is that reading a case is broad: advisers and T&C managers view every case, Tax and AQS, and both reviewer roles view both. So the scope stays Global and the *binding* changed — off `Authenticated Users`, which every account holds by signing in, and onto the seven roles that describe a job. An account with no role, or one whose role was withdrawn, now reads nothing. Reference tables keep their Authenticated Users binding, because a question's wording is not a client's file.
>
> Two Web API endpoints were closed as well: nothing addresses `/_api/al_responses` or `/_api/al_caseassignments`, and reachable-but-unused over a globally readable table is the worst combination — one request would have enumerated every answer on every case.
>
> The regression guard is **assertion 13** in `Check-PortalSecurity.ps1`, proved by injecting the regression and watching it name the file and the table. Verified live: DEV now shows 7 roles and no Authenticated Users on all four tables.

The original finding, for the record:

`Authenticated Users` is a role every logged-in contact holds automatically (`webrole.yml`, `adx_authenticatedusersrole: true`). It is granted **global-scope read** on the sensitive tables:

| Table permission | Scope | Roles |
|---|---|---|
| `Outcome Case - read all` | **GLOBAL** | Administrators, **Authenticated Users** |
| `Response - read all` | **GLOBAL** | Administrators, **Authenticated Users** |
| `Review Instance - read all` | **GLOBAL** | Tax Reviewer, AQS Reviewer, Administrators, **Authenticated Users** |
| `Remediation Action - read all` | **GLOBAL** | Administrators, **Authenticated Users** |

The Web API is enabled on those tables (`sitesetting.yml`: `Webapi/al_outcomecase/enabled`, `Webapi/al_response/enabled`, `Webapi/al_reviewinstance/enabled`, `Webapi/al_remediationaction/enabled` all `true`). Table permissions govern read, and these grant everything.

So an **Adviser** whose only business is their own remediation can `GET /_api/al_outcomecases` and read every client name, adviser, and date in the system — and `GET /_api/al_responses` for every answer to every check.

This also means fixes item 5's requirement ("check a T&C Manager cannot see cases they aren't mapped to") **cannot** be met by adding a dropdown: the read scope has to be narrowed first.

*Not introduced by this batch* — but squarely inside the audit's security question, and it makes several items' access controls moot.

**Fix:** narrow each of the four to a contact- or account-scoped permission bound to the specific business roles, and remove `Authenticated Users` from them. Keep global read only for genuine reference data (`Question`, `Question Version`, `Section`, `Review Route`, `Fail Reason`, `Outcome`).
**Effort:** ~1 day plus regression testing of every portal page, since several pages assume they can read any case.
