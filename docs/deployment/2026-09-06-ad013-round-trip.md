# AD-013 export-and-replace round trip — 2026-09-06

Source: `Env_AQ_Dev` (`https://org0b075da8.crm11.dynamics.com/`), exported as
`svc.automate.aq@ascotlloyd.co.uk`. **No environment write.** This changes `src/` only, and it
closes the gap that has blocked every promotion since 2026-09-03: `src/` was not the source of
truth.

---

## What was wrong

`al_Notification` was created through the metadata API on 2026-09-03 and had **no definition in
`src/Entities/` at all**. Everything built on top of it since — the drain step, the emitters,
`al_DrainNotifications` — was likewise in DEV and not in source. A managed promotion built from
`src/` would therefore have shipped plug-ins that reference a table the package does not create,
and the failure would have surfaced at run time in the target environment rather than at pack
time here.

## What ran

```
pac solution export --name OutcomeTesting --path <scratch>
pac solution unpack --zipfile OutcomeTesting.zip --folder <scratch>/unpacked --packagetype Unmanaged
```

Then the export was copied back over `src/`: `Entities`, `customapis`, `PluginAssemblies`,
`Roles`, `SdkMessageProcessingSteps`, and `Other/` (`Solution.xml`, `Customizations.xml`,
`Relationships.xml`, `Relationships/`). **Never `CanvasApps`** — AD-012 excludes it, because
packing a checked-in copy of the built bundle risks overwriting a newer published app with a
stale one.

## A quiet drift it found

30 custom API parameter and response files carried a **qualified** `<name>`:

```diff
-  <name>al_AssignCase.Reason</name>
+  <name>Reason</name>
```

DEV holds the bare name. `uniquename` was already correct in both, so nothing was broken and no
command misbehaved — but this is exactly the hand-authored-versus-emitted divergence AD-013
exists to remove, and it had gone unnoticed across every previous round trip because nothing
reads `<name>` at run time.

**Not found, and worth recording as a negative:** no `<plugintypeexportkey>` changed. The AD-071
trap — a committed key pointing at a plug-in type that no longer exists, which binds a Custom
API to nothing and executes silently — is not live.

## What was deliberately NOT brought into `src/`

The export now carries `powerpagecomponents/` (**248 components**) and `Assets/`, because the
Power Pages site was added to the solution on 2026-09-05 to prove the OD-034 export path. Both
were left out of `src/`, for two reasons, and this should be revisited rather than assumed
settled:

1. **The portal already has a source of truth in this repo** —
   `powerpages/outcome-testing---outcometesting/`, in the `pac pages` format, with readable
   names, id bands, and `Check-ComponentIds.ps1` guarding it. Committing 248 opaque
   GUID-named `powerpagecomponent.xml` files alongside it would create a **second
   representation of the same components with no guard and no way to tell which is
   authoritative** — a worse drift hazard than the one this round trip closes.
2. **It would pre-empt an open decision.** OD-034 explicitly leaves "adopt Power Pages solution
   ALM as the promotion path" undecided, because Microsoft documents the feature as preview,
   "not meant for production use", and the import side is still untested. Committing the
   artefact would settle that by accident.

**This is safe to leave out.** `Other/Solution.xml` does not declare the Power Pages components
as `RootComponents` — they travel as their own folder in the newer solution format — so their
absence does not break the pack, which is confirmed above. And an unmanaged import merges rather
than deletes, so a package built from `src/` cannot remove the site components from an
environment that has them.

## What this does not close

**AD-062, unchanged and still live.** `src/PluginAssemblies/` holds a committed DLL, and this
round trip is what put the current one back. Anything packing the whole of `src/` for an
**import** must strip `PluginAssemblies/` first, or the import replaces the live assembly with
whatever was last committed — at the same version and public key token, so nothing reports it.
The pack above was a verification, not a deployment.

**OD-011 is not closed by this either.** `src/` being correct makes a promotion *possible*; it
does not make TEST or PROD exist. Per project owner direction 2026-09-06, those are set up once
everything is tested and approved in DEV.
