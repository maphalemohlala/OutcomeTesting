{% comment %} Outcome cards and their drill-down (PP-17, BR-005, BR-010, FR-032). A case's grade is on al_outcome, and BR-007 splits it across two columns so a regrade preserves the original. The grade in force is therefore final where one has been recorded, otherwise initial - the same precedence Outcomes.EffectiveOutcome applies server-side. In FetchXML that is an OR whose second branch is an AND, once per grade. Counted as distinct cases, not as outcome rows, because the card is answering "how many cases" and the drill-down lands on a list of cases. Both halves have to count the same thing or the number on the card will not match the number on the page it opens. Six small aggregates rather than one grouped query. A single query grouped by both outcome columns would be fewer round trips, but it would make the page depend on how an aliased choice column renders in Liquid - and a card that silently shows "120910711" instead of a grade is worse than a fifth aggregate. Every value below is a numeric literal from src/Entities/al_Outcome/Entity.xml; nothing here reads an option set back. Ungraded is total cases minus cases carrying an outcome row, taken as its own count rather than as "everything the four cards did not match". A case whose outcome row somehow held neither grade would otherwise be quietly added to Not yet graded, where nobody would look for it. {% endcomment %} {% fetchxml count_pass %} {% endfetchxml %} {% fetchxml count_issues %} {% endfetchxml %} {% fetchxml count_insufficient %} {% endfetchxml %} {% fetchxml count_harm %} {% endfetchxml %} {% fetchxml count_cases %} {% endfetchxml %} {% fetchxml count_graded %} {% endfetchxml %} {% comment %} An aggregate fetch returns no result set at all when the caller cannot read the table, and indexing entities[0] straight away then fails with "Index was outside the bounds of the array" - which renders as the card's number.
