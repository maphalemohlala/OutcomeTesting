Guards written, never wired

A review of the Outcome Testing solution found eight critical defects. The recurring shape is not missing logic — it is correct logic that nothing calls, and permission gates that open when their data is absent.

What the toolchain says

The build is clean. Every defect below is a logic or design fault that compiles and passes its tests — which is precisely why they need reading rather than running.

tsc -b Clean. No type errors across 99 TypeScript files.
vitest run 12 / 12 passing — but the only test file is permissions.test.ts. The business-rule module and every plugin are untested.
eslint . 0 errors, 9 warnings — all one useMemo perf pattern. Not correctness.
dotnet build Both projects succeed — 0 warnings, 0 errors (SDK 10.0.400, Release). Every C# defect below is in code that compiles cleanly.
assembly diff Fresh build 49,152 bytes / 13 plugin types. Shipped solution assembly 47,104 bytes / 11 types. The solution ships a stale build.

Two root causes behind most of it

Fixing these two patterns closes roughly two thirds of the findings. Treating them as separate tickets means fixing the same bug a dozen times.

1. Nothing paginates — in either tier

PageInfo, PagingCookie and MoreRecords appear nowhere in the plugin assembly, and every client read is a bare top: cap. Dataverse returns 5,000 rows and stops.

  • The regulatory export truncates silently. GenerateExportPlugin writes 5,000 rows, then stamps al_rowcount with the truncated figure — so reconciliation cannot detect the loss.
  • The case worklist caps at 200, oldest-first. Past 200 cases, new work stops appearing in the primary queue entirely.
  • Dashboard, MI reports and permission rules all aggregate over one unpaged page with no truncation indicator.

2. Permission gates fail open when their table is empty

Both the client and the server treat "no role data" as "allow everything". Each is deliberate and commented as a bootstrap path — but neither is limited to bootstrap. A deactivated mapping table or a failed read re-opens the gate at any time in the system's life.

  • Server: zero active role mappings means every guarded command accepts every caller.
  • Client: an empty or unreadable mapping table grants all six roles to everyone.
  • The guard that would fix the client half already exists — a ready flag, computed and never read.

Critical

All eight verified against source. These block a production promotion.

C1

The solution ships a stale assembly, so two commands call code that isn't deployed

Verified by build

app/src/services/commands/users.ts:61, :84 — src/customapis/ — src/PluginAssemblies/

The admin screen calls al_UpdateUser and al_SetUserActive. Building the plugin project settles the root cause: the source compiles fine and produces 13 plugin types, but the assembly committed into the solution has only 11.

                          FRESH BUILD   SHIPPED SOLUTION
bytes                          49,152             47,104
SetUserActivePlugin                 1                  0
UpdateUserPlugin                    1                  0
(the other 11 types)                1                  1

Someone added the two plugins and never re-packed the solution. The matching Custom API definitions were never created either — src/customapis/ holds 11 folders, and the registration tool names neither message.

What breaks Renaming a user and deactivating a leaver — the sanctioned OD-010 retention path — both fail at runtime behind a generic "service unavailable" message. Revoking a departed reviewer's access is impossible through the app.
C2

Server permission gate allows everyone when no active role mapping exists

Verified

plugins/OutcomeTesting.Plugins/PermissionHelpers.cs:39-51

EnsureAppPermission returns — meaning allowed — whenever al_userrolemapping holds zero rows with statecode = 0. This is the only application-level authorisation on every guarded command.

The inline comment argues that Dataverse create privilege on the mapping table still gates who reaches here. That holds for role assignment, but not for the commands that write to other tables — case edits, exports, question retirement.

What breaks An administrator deactivates the last role mapping, or a migration lands mappings as inactive. Every RBAC-gated command now accepts any authenticated caller — including al_AssignUserRole, so a user can grant themselves Administrator.
C3

The plugin signing private key is committed to the repository

Verified

plugins/OutcomeTesting.Plugins/OutcomeTesting.Plugins.snk (1,172 bytes, git-tracked)

The file header confirms a full private key blob, not a public-key-only file:

07 02 00 00 00 24 00 00 52 53 41 32
^^ PRIVATEKEYBLOB              "RSA2" = private

Building with the committed key closes the loop — it reproduces exactly the identity the registration tool hardcodes:

built from the committed .snk → PublicKeyToken=86b764d5a2430b1f
Program.cs:133, :359          → "86b764d5a2430b1f"   ← match

So anyone with repository read access can build an assembly Dataverse accepts as an in-place update of the registered one, at the same version and public key token.

Judgement Strong-naming is not a .NET trust boundary, and exploiting this still requires Dataverse deployment privileges on the org — so this is a defence-in-depth failure, not an open door. But the plugins are the only enforcement point for regrade, sign-off and role assignment, and they run with system privileges. Rotate the key, remove it from history, and inject it at build time.
C4

The Trail Light export silently truncates at 5,000 cases

Verified

plugins/OutcomeTesting.Plugins/GenerateExportPlugin.cs:77

The Closed-case query is a single RetrieveMultiple with no paging loop, so Dataverse returns at most 5,000 rows. The batch is then stamped al_batchstatus = Generated and al_rowcount = <truncated count>.

What breaks With 7,400 closed cases, 5,000 export and the batch reports 5,000 as its complete row count. The regulatory file is 2,400 cases short and the record of it claims to be whole — reconciliation cannot detect the gap. Re-running reproduces the same truncation.
C5

CompleteRemediation runs as the system user with a bypassable owner check

Verified

plugins/OutcomeTesting.Plugins/CompleteRemediationPlugin.cs:56, :154

Every read and write uses PluginUserService (system), there is no EnsureAppPermission call, and the sole authorisation short-circuits when the owner is not a systemuser:

if (owner != null && owner.LogicalName == "systemuser"
    && owner.Id != context.InitiatingUserId)

al_RemediationAction is user-owned, so ownerid can legitimately hold a team reference.

What breaks For any team-owned remediation action, the check passes for everyone. Any authenticated caller can drive it to Completed, executing as the system user so their own lack of write privilege never applies. The action becomes eligible for sign-off with no adviser having done the work.
C6

Custom roles are inert server-side — the UI and the server disagree

Verified

PermissionHelpers.cs:103, :112, :136 vs AssignUserRolePlugin.cs:76

The assign and permission paths write custom roles to al_rolecode, leaving al_approle null. The resolver reads only al_approle and filters page permissions on it alone. Four of the ten seeded roles have no al_approle value at all.

What breaks An admin grants "Senior Checker" Edit on cases. The client resolves it from al_rolecode and enables the edit buttons. The user clicks Save and the server replies "You have no application role assigned" — immediately after one was assigned.
C7

The documented deploy script cannot succeed

Verified

plugins/deploy/Register-CompleteRemediation.ps1:63, :66, :102

Get-OrCreate derives the primary-id column from the entity set name rather than the logical name, producing properties that do not exist — customapisid instead of customapiid.

Get-OrCreate -Set 'customapis' …
  → $select=customapisid
  → HTTP 400  "Could not find a property named 'customapisid'"

With $ErrorActionPreference = 'Stop', the script aborts before creating the Custom API.

What breaks The documented deployment path fails on every run, on a fresh org or an existing one. Step 1 also points at an spkl.json that exists nowhere in the repo, and discards the resulting error with 2>$null.
C8

A seed data package ships a single-plugin assembly that would overwrite the live one

Verified by decode

data/plugin-register/data.xml:11

Decoding the base64 content blob confirms it:

decoded bytes: 15,360
plugin types : CompleteRemediationPlugin, ExecuteDataversePlugin, IPlugin

One command plugin, against 11 in the shipped solution assembly and 13 in a fresh build. Because the package upserts pluginassembly matched on name — at an unchanged version and public key token — Dataverse accepts it as an in-place replacement.

What breaks Running pac data import on this package after registration leaves 10 of 11 commands pointing at plugin types absent from the assembly — every regrade, sign-off, role assignment and case edit failing at runtime, with no schema change to explain it. The blob also embeds a developer's absolute path.

I2

The client-side business-rule module is dead code

Verified

app/src/types/domain.ts

Nine of fourteen exports have zero callers anywhere in app/src:

requiresRemediation          PRIVILEGED_OUTCOME_ACTIONS

I3

Import batch completion is written without checking the result

Verified

app/src/features/imports/useCaseUpload.ts:216-220

The closing update that marks the batch Completed and persists its counts is awaited but its .success is never inspected — unlike every other write in the same file.

What breaks On failure the user sees a success summary while the batch stays at Validating with stale counts, contradicting the "imports are logged and recoverable" invariant.
I4

Deactivating a user does not revoke their access

Verified

SetUserActivePlugin.cs:64-68 vs PermissionHelpers.cs:99-107

Deactivation flips only al_user.al_isactive. The resolver looks up al_userrolemapping by work email and never consults al_isactive, so the mappings stay active.

What breaks A leaver deactivated through the sanctioned path keeps every application permission for as long as their Dataverse account exists — including a T&C Manager's ability to overwrite a final outcome. (Compounded by C1: the deactivate command does not even reach the server.)
I5

Verified

canManage wraps the buttons at lines 230 and 256, but "Assign a role" and "Set a permission" — which open equivalent privileged-write modals — render unconditionally. Cosmetic given server enforcement, but inconsistent within one page.

I6

A Review Instance can exist with no owning case

Verified

src/Entities/al_ReviewInstance/Entity.xml:99

al_outcomecaseid is RequiredLevel=none, while the same lookup on Outcome, RemediationAction, CaseAssignment, Signoff and ExportRecord is required. The domain notes record this link as "not built yet" from when Outcome Case did not exist; it was added without tightening the level.

What breaks A review and its whole answer set can be orphaned from any case — invisible to the worklist, to the Tax-then-AQS sequencing check that reads sibling instances, and to the export.
I7

The verification harness mutates live records and leaves immutable audit events

Reported

plugins/OutcomeTesting.Registration/Program.cs:205-224, :438-447, :520-599

All three verify modes select the first record in al_outcomecase with no filter and no environment guard, then create and mutate real business records against it. The finally deletes the seeded outcome and review instance — but the audit events the commands wrote are immutable and stay attached.

What breaks Running verifyregrade against production leaves permanent audit events on a real client case recording a regrade from Insufficient evidence to Pass that never happened. The audit trail AD-031 exists to protect is falsified, and MI cannot distinguish it. The CompleteRemediation path has no finally at all, so a failure strands a fake open remediation action that blocks sign-off.
I8

No lifecycle transition guard exists on either tier

Reported

plugins/OutcomeTesting.Plugins/UpdateCaseDetailsPlugin.cs:92, :283

al_casestatus is written straight from caller input with no source-to-target validation, and the review route is freely settable mid-review.

What breaks A case can jump from Imported directly to Closed, skipping validation, allocation, review and remediation — then be picked up by the export (which filters on Closed) and delivered with no review instance and a blank grade.
I9

Sign-off is unlimited and reversible

Reported

plugins/OutcomeTesting.Plugins/SignOffRemediationPlugin.cs:88

The only precondition is that the action is Completed, and an Approved sign-off leaves it Completed — so nothing stops a second sign-off. A later Rejected one reopens an already-approved action, leaving two contradictory sign-offs with nothing marking which is authoritative.

I10

Nine of the twenty contracted export columns are never populated

Reported

plugins/OutcomeTesting.Plugins/GenerateExportPlugin.cs:83-101

Only 11 of the AD-039 columns are written. al_filequalitygrade and all eight fail-accountability name/code pairs are declared on al_ExportRecord but never set — so every delivered row breaches the fixed column contract and no failure can be attributed.

I11

The idempotency key is not scoped to a command or a target record

Reported

plugins/OutcomeTesting.Plugins/CommandHelpers.cs:73

FindAuditByKey matches on al_idempotencykey alone across the whole audit table, and the key column carries a unique alternate key — so the key space is global. Callers then build a success response from the requested target rather than the audit's recorded one.

What breaks Replaying a key already used by a different command returns a fully successful-looking response for an operation that never ran. The keys are caller-supplied on unbound, non-private APIs.
I12

Creating a user resurrects a deactivated leaver

Reported

plugins/OutcomeTesting.Plugins/CreateUserPlugin.cs:65-70

CreateUser upserts on work email with a payload that always sets al_isactive = true and statecode = 0. Re-adding someone with a leaver's email reactivates the old record under a new display name, restoring their still-active role mappings — audited only as "Created".

I13

Regrade does not require an initial outcome to exist

Reported

plugins/OutcomeTesting.Plugins/RegradeCasePlugin.cs:71

The outcome is retrieved and the result discarded — nothing checks it was ever graded. A final outcome can be written with no initial to compare against, breaking BR-007 from the other side and producing an audit event claiming an override that never happened.

I14

Export is re-runnable over a delivered batch

Reported

plugins/OutcomeTesting.Plugins/GenerateExportPlugin.cs:109

No guard on al_batchstatus, and records are upserted in place. Re-running after a delivery rewrites the delivered rows with current values, restamps al_generatedon and reverts Delivered to Generated — destroying the record of what was actually sent.

I16

Client permission resolution has an unused readiness guard

Verified

app/src/app/permissions/permissionContext.ts:6 · PermissionProvider.tsx:44, :81, :93

ready is declared and computed but consumed nowhere. While unresolved — and whenever the mapping read fails — the provider hands out the union of all six roles, so route gates pass.

Judgement The fail-open is deliberate and documented, and AD-041 makes UI gating explicitly advisory. The genuine issues are that the exposure is not limited to bootstrap, and that the guard designed to close the window was never wired up.

Checked and found correct

Worth recording — these were audited against the domain rules and hold up. Several are the kind of thing that is usually wrong.

Checklist cascade behaviour

All configuration relationships are Restrict at every level, as AD-016/AD-017 require.

Fail Reason cardinality

A true many-to-many with Response, not a lookup — matching AD-025 and FR-013.

Initial vs final outcome

Both columns exist alongside the regrade reason and timestamps. BR-007 is representable.

Alternate keys

Ownership model

Configuration tables organisation-owned, operational tables user-owned, per AD-024.

Auditing

Enabled on all 23 tables, including every sensitive and lifecycle table named in the rules.

V8 seed data

Counted, not assumed: 1 / 1 / 11 / 42 / 42 / 20 — exactly AD-027. Response types, mandatory flags and fail-reason categories all match the transcript.

Seed data hygiene

Ten fictional users on @example.com. No personal data, no tenant or environment GUIDs.

Custom API contracts

All 11 match their JSON contracts on binding, privacy and parameter optionality. Mandatory reasons are mandatory.

Access-level comparison

Case edit path

Routed through the server-enforced al_UpdateCaseDetails command with concurrency and audit — not a client record write.

Hardcoded environment IDs

The appId and environmentId in power.config.json are a documented, correctly scoped AD-007 exception — not a violation.

Limits of this review

What is proven, and what is not

  • All eight Criticals are verified. Three now carry build-level proof rather than source reading: the stale shipped assembly (C1), the key-to-token match (C3), and the decoded seed blob (C8).
  • The C# compiles, but was never executed. Both projects build with 0 errors, so every plugin defect is in working, shipping code — but no plugin was run against a Dataverse org. The logic findings (C2, C5, C6 and the plugin Importants) are static analysis against quoted source: high confidence, no runtime trace.
  • Chips mark provenance on the Important findings — which I re-verified against source myself, and which I am relaying from a reviewer after confirming it was internally consistent and quoted real code.
  • Runtime privilege behaviour is out of reach from source. Several findings are bounded in practice by Dataverse table privileges and row-level security, which cannot be read from this repository. Where that changes severity, I have said so in the finding.
  • Building created untracked output under plugins/*/bin and obj — which the root .gitignore does not match, per I15. Worth clearing before committing.
